---
name: Preference Enforcement
description: Strict cuisine guard, hours backfill (40 venues + coalesce), anti-repeat from places_usage with special-request allowlist bypass, varied curated rotation
type: feature
---
- **Cuisine guard:** `selectActivitiesForExactDailyCount` and `preserveExactDailyCountWithMeals` accept `requestedCuisines` and DROP any meal whose name/desc/category/address doesn't match at least ONE cuisine via `activityMatchesRequestedCuisines`.
- **Hours backfill:** `enrichMissingOpeningHours` runs up to 40 parallel SerpAPI/Serper lookups within a ~9.5s budget; outer wrapper allots 11s. Final coalesce pass copies `operating_hours` / `open_state` / `hours` onto `openingHours` so the UI never shows "Hours unavailable" when SerpAPI returned ANY usable signal.
- **Anti-repeat:** `__recentlyUsedPlaceIds` pre-loaded from `places_usage` (per user + city). Hard rejection sites all consult `__isAllowedBySpecialRequest` — phrases extracted from `specialRequestInjections.query` (incl. quoted tokens) bypass the blocklist so a user-named venue can re-appear.
- **Curated fallback variety:** All three CITY_PLACES fallback loops (curated-fill, relaxed-fill, final-exact-fill) now offset their rotation by `__serpVariationSeed % poolLength` so identical inputs surface different landmarks across regenerations. The seed is XOR-randomised in `resetSerpRequestState` on every run.
- **Hours UI policy:** Frontend `isPlaceholderHours` (in `src/components/ItinerarySchedule.tsx`) treats ONLY truly-empty/unknown tokens as placeholder. The curated landmark/SerpBank/guaranteed-fill loops NO LONGER inject the fake `"10:00 AM - 10:00 PM"` string — they pass SerpAPI's real `hours` / `open_state` / `operating_hours` (object) fields verbatim. The backend MUST mirror `operatingHours` (camelCase) onto `operating_hours` (snake_case) on every activity — the frontend `getUnifiedOpeningHours` checks BOTH names plus `_raw.operating_hours` so the rich per-day schedule object renders correctly. The post-enrichment final-coalesce pass enforces this mirror automatically. Inventing generic hour ranges is forbidden.
- **Cross-day place identity now includes address:** `__placeIdentities` returns `addr:<normalized address>` (when ≥8 chars) in addition to place_id / data_id / name / geo. Two activities at the same postal address — even with different times or categories — are now rejected as duplicates within a run AND across regenerations, unless `__isAllowedBySpecialRequest` matches.
- **Strict no-repeat fallback fills:** The curated `anti-repeat-fill` and `guaranteed-fill` loops now reject ANY candidate whose `__placeIdentities` overlap `__usedPlaceIdsThisRun` (cross-day) OR `__recentlyUsedPlaceIds` (cross-generation), unless `__isAllowedBySpecialRequest` returns true. The previous 2-pass design that relaxed the recently-used block on pass-2 has been removed — a day may end up shorter than the target, but it is NEVER padded with a place the user already saw.
- **Source-type-first classification in fallbacks:** Both fallback loops now call `inferCanonicalCategory(lmShape, selectedInterestSet)` to upgrade the curated landmark's coarse `category` using SerpAPI `type/type_id/types` from `lm._raw`. A theme park whose curated `category="nature"` is corrected to `entertainment` because its raw `type_id` is `amusement_park`. The `lmShape` now also forwards `_raw` and the place type fields so `inferDominantPlaceCategory` can read them.
- **Allowlist lifecycle:** populated right after `extractSpecialRequestInjections`, cleared in `resetSerpRequestState` between runs.
- **Strict special-request validation:** `itineraryViolatesPreferences` now treats ANY unmatched user special request as a HARD violation (was a soft warn). The post-validation block then runs a **targeted slot refill** that swaps ONLY non-matching, non-meal, non-interest-aligned activities for SR placeholders (`__slotRefill: true`) and re-validates. If that resolves the violation we keep the partial itinerary instead of rebuilding the whole thing — fulfilling "regenerate only the missing slots instead of keeping unrelated activities." Only if the targeted refill cannot satisfy the SRs do we fall through to `createFallbackItinerary` (the heavy rebuild).
- **Cross-generation history dedup:** `places_usage` rows are written for EVERY activity in the final itinerary (meals included) at the end of the run via `touch_place_usage`. The city written to `p_city` MUST equal the original `destination` string passed to the function (not `day.cityName`) so `__loadRecentlyUsedPlaceIds` finds them on the next run for the same city. Special-request allowlist phrases bypass this blocklist so a user-named venue can be re-suggested explicitly. **Single-activity and day regen flows now ALSO persist via the `__regenResponse` wrapper** — every one of the 11 regen return points fires `touch_place_usage` for the picked place(s) before returning, so re-clicking "regenerate" on the same slot can no longer return the same place.
- **Client-side auto-retry on busy/timeout:** All four `generate-trip` invoke sites (`TripWizard`, `PromptTripPlanner`, `ItinerarySchedule`, `ItineraryPage`) now retry transient failures (gateway 502/503/504, fetch/network/abort, "non-2xx", upstream/busy) with exponential backoff (1.5s → 3s → 6s, +jitter) and a 45-60s per-attempt budget. The shared helper lives in `src/lib/invokeWithRetry.ts` and is used by `PromptTripPlanner`. The other three sites have their own inline retry loops with the same defaults (3 retries, 45-60s timeout). Business-logic errors (quota/limit/exhausted/invalid) are NOT retried.
